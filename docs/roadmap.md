# 路线图

里程碑按顺序做。后一个里程碑开始时，前一个的验收还成立。日期不排，完成标准以下列交付为准。

## M0 — 设计

**状态：进行中（本文档即此阶段的交付）。**

交付：

- [需求](requirements.md)
- [架构](architecture.md)
- [包格式](package-format.md)

完成标准：实现第一期时不再重新选择界面技术、工作格式和布局规则。若要推翻 Rust 核心 + Qt 5.15、临时目录里的工作副本、不压缩 zip 的 `.etpk` 文件，或“自动排布 + 可选固定起点”，先改这三份文档再写代码。

## M1 — 可编辑的镜像包

对应需求里的全部 P0。

交付：

- `et-core`：在临时目录创建工作副本，把工作副本打包成 etpk 文件或从文件解包，布局、校验、流式复制镜像、路径检查。
- Qt 5.15 应用：分区表编辑、元数据里的名称和容量展示、保存与另存为、未保存提示、撤销/重做。
- 三平台构建说明：Windows 7 SP1 x64、macOS、Ubuntu 22.04。Windows 构建必须在 Windows 7 SP1 上能启动。
- `et-core` 单元测试覆盖架构文档第 7 节。

不做：改分区顺序、固定起点的界面、GPT 二进制、下载。保存和打开已经使用不压缩的 zip。

建议实现顺序：

1. 内存中的文档、布局函数和校验，先不碰磁盘。
2. manifest 读写和原子保存。
3. 镜像复制、删除和 `.trash` 撤销。
4. Rust 命令层和 C ABI，返回 `DocumentView`。
5. 分区表界面，按需求第 7 节做手工验收。

## M2 — 把包变成可烧录的描述

对应 P1，以及 P2 里不依赖 USB 的那一部分。

交付：

- 调整顺序、固定起点、分区类型和属性的编辑。
- 容量、扇区大小、对齐可改，并立即校验。
- 由校验通过的包生成主 GPT、备份 GPT 和可选的用户区 raw 镜像（镜像空洞按分区大小留空，不把缺失镜像当成零填充以外的错误；无镜像分区在 raw 里保持零）。
- 可选的流式 SHA-256，写入 manifest 的可选字段 `imageSha256`（格式文档到那时再加这一字段，主版本不变）。

完成标准：同一包在三套系统上生成的 GPT 字节一致；用单独的测试向量核对第一条分区起点和备份 GPT 位置。

## M3 — 下载

对应 FR-DL。协议一个一个加，不在这一里程碑开始时承诺厂商清单。

交付：

- `UserAreaWriter` 与 `ImageSource` 接口。
- 一个默认后端：导出的 raw 镜像，或 Linux 上写入块设备。块设备写入需要显式确认目标设备路径和容量，容量小于包的 `userAreaBytes` 时拒绝。
- 下载入口只接受无校验错误的包。
- 厂商协议作为可选后端接入，每个协议单独的构建 feature 和一份说明（进入哪一种下载模式、写哪些分区、失败怎么停）。

完成标准：至少一种后端能把 M2 生成的布局写到真实介质或回环设备，读回的 GPT 与分区镜像和包一致。

## 明确不做

除非需求文档先改，否则这些不进上述里程碑：

- 在工具内修改文件系统内容
- 多人协作编辑同一包
- 自动识别插入的板卡并选择协议
- 把厂商私有 update 包当作原生工作格式

厂商包如果以后要支持，只做“导入成 `.etpk`”的单向转换，放在 M3 之后单独开里程碑。
